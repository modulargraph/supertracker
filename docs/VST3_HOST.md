# Original VST3 host

SuperTracker hosts macOS VST3 components through its own C++/Objective-C++ adapter in `Sources/VST3Host`. It uses the official Steinberg SDK's ABI headers and FUID implementation, under the SDK's MIT license. It does not use JUCE. The Swift `VST3AudioUnit` is an AVAudioEngine graph adapter, so AU and VST3 instruments/effects share the existing routing, automation, sends and compensation.

The C interface is `Sources/VST3Host/include/VST3Host.h`. It provides bundle/class discovery, component/controller lifecycle, float stereo processing, sample-offset notes and parameters, MIDI CC/pitch-bend mapping, parameter discovery, component/controller state, raw component-state import, and Cocoa editor attachment. The render implementation uses preallocated event and parameter storage and bounded UI-to-audio queues. The indexed-input API accepts separately activated mono/stereo auxiliary buses using their actual plugin bus indices and metadata. Main input lookup uses the reported bus type, including layouts where auxiliary bus 0 precedes the main bus. Omitted, inactive and null inputs are cleared to silence every callback. Extra outputs are discarded; multi-output routing remains unsupported.

## State and control semantics

- The project snapshot includes component and controller state, with the exact VST3 class ID in a bounded envelope. A mismatching ID is rejected before changing the plugin.
- Controller state may be absent when `getState` returns `kNotImplemented` without writing bytes, matching the SDK base controller. Any other failed controller save aborts the snapshot with null output and zero size. This host also rejects nonempty `kNotImplemented` output: an unsupported partial stream is not treated as a restorable controller state. Complete and optional-empty states, failure codes and partial writes have dedicated original-component tests.
- Generic UI parameter edits can be saved before audio starts using the standard VST3 zero-sample parameter flush before collecting processor state. The exact compatibility exception below refuses this path because that component reads the value without reliably persisting it.
- Exact Massive X class and loaded bundle release 1.7.1 uses an explicit asynchronous capture protocol. Running graphs first deliver edits through ordinary callbacks. An already stopped, quiesced graph may explicitly prepare one discarded 4,096-frame block, provided no notes are held. In either case the main loop must then be allowed to progress for one second before capture. Queue emptiness does not imply that the vendor model has settled. Other versions/classes retain standard zero-frame capture.
- Saving while the graph runs never pauses it (`st_vst3_copy_state_concurrent`). `getState` is a UI-thread call that VST3 plug-ins must serve concurrently with `process()`, as every DAW saves while playing. The host never runs its own flush block in this mode, because the UI-edit ring has exactly one consumer: the render thread. While edits are still queued it copies nothing, and the rack retries for up to 50 ms of audio blocks. Only if audio is not delivering them does it fall back to the drained, paused capture. Before this, every autosave and every project publication paused the graph once per VST3 instance. With the hardware-editor template that made playback stutter every few steps.
- The rack remembers the encoded state it last read from each live unit. A desired state equal to that is the unit's own output, so reconciliation does not restore it again: doing so would pause audio and could only revert later edits. Change notifications after reconciliation (`plugins.changed`) report these known states and never read the plug-ins.
- Controller component-state synchronization accepts `kResultOk` and the SDK-supported optional `kNotImplemented`. Explicit failure aborts creation/restoration; a failed restore remains unavailable for profiled capture. The SDK base controller and `PresetFile::restoreComponentState(IEditController*)` establish these return semantics. Original tests cover explicit failure before and after reading state, safe capture refusal, and successful recovery.
- Controller values have an atomic cache for the audio adapter. Processor-originated updates are copied into the controller by a main-thread tick.
- Raw NKS state is passed only to an explicitly matched component. Returning success from `setState` alone is not proof that a preset sounds correctly or that the plugin can shut down safely.
- Host reset first sends tracked note-offs and sustain release, because `setProcessing(false)` does not guarantee a MIDI panic in every plugin. Even when the graph is already stopped, reset briefly enables processing for a discarded one-frame panic. This private reset process leaves the UI queue untouched; pending static edits reach the first ordinary render after the stop/start transition. An explicit generic state save still performs its own parameter flush; the exact compatibility profile requires the explicit capture preparation described above. Stopping or exporting must preserve the selected sound.
- MIDI CC assignments are used only when the component returns success. Output IDs from failed calls are discarded, including zero: otherwise an unmapped panic CC could overwrite an unrelated macro parameter.

## Indexed auxiliary-input contract

Bus metadata and activation are control-thread operations with rendering quiesced. Configuration checks the current mono/stereo layout rather than silently renegotiating it. `activateBus` occurs after `setupProcessing` and while the component is inactive, as required by the SDK. Changing one input temporarily deactivates the component, checks activation and reactivation, and rolls back on recoverable failures. An irrecoverable failure leaves processing stopped. Preparation and unchanged state restoration retain configured activations; a state-induced layout change fails before rendering can use stale buffers.

`tests/vst3_sidechain_tests.sh` builds original effect fixtures, including an auxiliary input at index 2 and an auxiliary-at-0/main-at-1 layout. Tests cover stereo and mono keys, exact first/last-sample cancellation, shifted-input timing, activation failure that mutates before returning an error, inactive/default-active inputs, omitted/null channels, duplicate/invalid descriptors, state and prepare retention, unsupported layouts, and zero C++ allocations during rendering. The strict fixture rejects activation outside the SDK lifecycle; the previous order fails initialization. Both ordinary and ASan/UBSan builds pass. The suite is included in the complete original-fixture runner and does not load installed plugins.

## Lifecycle audit, 9 October 2026

The implementation was compared with the pinned official SDK sources:

- `Vendor/vst3sdk/public.sdk/source/vst/hosting/module_mac.mm`: load the CFBundle, call `bundleEntry`, acquire the factory; on destruction release the factory, call `bundleExit`, then release the bundle. The official sample does not explicitly call `CFBundleUnloadExecutable` in this sequence.
- `Vendor/vst3sdk/public.sdk/source/vst/hosting/plugprovider.cpp`: initialize a combined component/controller only once, connect only distinct components/controllers, disconnect before termination, terminate the component before a distinct controller, and then release interfaces.

The host now follows those rules. It also keeps one module per path, preventing `bundleExit` while another instance uses the module. A module-owned host context lives as long as the factory; factories no longer retain a pointer to an already destroyed instrument instance. The factory, component and controller receive that same host context, matching the SDK's shared host identity; each controller receives its separate per-instance component handler.

Explicit shutdown matters. The module cache can be constructed before a vendor lazily registers global destructors. Leaving cache cleanup until C++ process exit can therefore allow vendor globals to disappear before host module cleanup. `st_vst3_release_unused_modules()` releases only modules whose shared ownership count is one (the cache itself). Hosts must first stop rendering, drain registered render readers, close plugin handles, and then call this function on the main thread before application teardown. Scanner helpers use the same explicit cleanup. The standalone smoke harness now uses RAII to perform this sequence on both normal return and exceptions.

The production rack's `closeAllPluginsAfterStop()` closes actual VST3 handles even if AVFoundation still retains graph adapter objects. `AudioHost.shutdownAndWait()` stops the graph and waits for active render readers before closing handles and releasing unused modules. Native graph regression tests verified ordinary process exit after this explicit shutdown barrier; cleanup does not depend solely on Swift `deinit` running at process exit.

## Earlier evidence and investigation

The original deterministic fixture passes in both success and injected-initialization-failure processes. Its log proves this ordering: every created component is terminated and destroyed; then the factory is destroyed; then `bundleExit` runs; then plugin static destruction runs. Multi-instance tests also prove that releasing the module cache while one instance remains does not unload its factory, the factory host context stays valid after components die, and a combined component/controller is not connected to itself. The same fixture verifies an immediate parameter edit followed by save/reopen without intervening audio, exact note offsets, reset panic, and wrong-class state rejection. Core and lifecycle tests also pass with AddressSanitizer and UndefinedBehaviorSanitizer.

`tests/vst3_core_tests.mm` checks stream boundaries, fixed queue capacities, parameter ordering/coalescing, exact MIDI/automation offsets, pitch-bend conversion, panic note-offs, and zero host allocations during rendering. These tests load no installed third-party plugin.

The lifecycle fixture also verifies editing a stopped plugin followed by reset, first-note PCM, save and fresh-instance restore. This regression failed the previous implementation, which skipped panic while stopped and discarded the pending parameter queue. The corrected implementation produces exact edited PCM, releases the old held note and restores the edited parameter cache in normal, deferred-controller and deferred-initialization fixtures.

The subsequent reset refinement keeps static edits out of the panic block altogether. An original fixture reads a one-frame parameter update but defers its commit until ordinary processing, then clears that internal pending work when processing stops. The prior reset consumed the edit in its panic and produced old gain 0.875 instead of 0.625 after restarting; preserving the host queue until the ordinary block fixes both active and stopped reset cases. Core tests also inject failures at initial start, panic processing, stop and restart: every case preserves the ring's original read/write indices, and the next successful normal process receives the queued value. This fixture demonstrates the reset ordering problem without asserting undocumented Massive X internals.

A second fixture makes a failed MIDI assignment write a valid parameter ID, including exact ParamID 0. Ignoring that failed status reproduced a panic overwriting edited gain (expected 0.625, actual 0). The corrected host passes those fixtures and retains successful MIDI mappings. This establishes the host defect and its mechanism; it does not establish that Massive X returns that particular invalid output.

Optional `st_vst3_watch_parameter` diagnostics trace one exact ID through queued UI edits, scheduled automation, MIDI mapping, final merged process input and actual component `getPoint` reads. Fixed atomic storage is disabled by default; render performs no logging, allocation or locking. A read proves delivery rather than semantic application. Core tests distinguish same-offset UI/automation/MIDI coalescing, while lifecycle tests verify queue/read/PCM/state agreement across stop, reset and fresh restoration. Swift can retrieve passive snapshots without flushing the queue.

The compatibility gate reads `CFBundleShortVersionString` from the actual loaded module and compares the entire value exactly; project metadata cannot enable it. Factory and bundle versions are exposed separately because the installed VST3 factory does not report the same string as its public bundle release. The first native immediate-save attempt did not exercise the compatibility flush because its incorrect factory-version gate returned zero required frames. A subsequent guarded test verified actual factory version `1.7.1 (R0)`, bundle release `1.7.1`, and a 4,096-frame read of edited value 0.47, but serialized and fresh-restored state still contained 0.0740625. A subsequent guarded one-block test followed by a one-second MainActor suspension passed all six native groups with normal exit zero: macro 0.47 was present in opaque component state and in a fresh instance before any export, while no audio processing occurred during the suspension. This evidence is specific to the loaded class and release; it does not establish the vendor's internal synchronization mechanism.

The C++ transaction records an atomic edit generation and a distinct preparation token. Dirty state survives both ordinary and explicitly permitted synthetic delivery. Beginning an attempt records its generation and a monotonic deadline. After the required main-loop suspension, authorization checks the token, generation, empty queue and deadline. A one-shot capture consumes that authorization, checks again after component/controller serialization, and acknowledges the generation only on success. Cancellation, a failed save, a newer edit or a stale async caller cannot acknowledge dirty state. Retrying an already delivered edit waits again without processing extra audio. A failed, potentially partial state restoration blocks this exact profile's capture until a valid state is restored or the component is reloaded.
