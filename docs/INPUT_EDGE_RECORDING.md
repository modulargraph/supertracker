# Applied input-edge recording clock

Status: opt-in core API and pure regressions implemented. The existing `st_engine_note_on`, `st_engine_note_off`, `STEvent` layout and ordinary playback API remain unchanged. AudioHost and frontend must explicitly adopt this protocol before it supplies live recording positions or gates.

`st_engine_input_note(engine, requestID, edge, track, instrument, note, velocity, applyNote)` queues one input edge. `requestID` is nonzero and strictly increasing over that engine's lifetime, including across project replacement; only successfully admitted IDs advance the counter. Edge is `ST_INPUT_NOTE_ON` or `ST_INPUT_NOTE_OFF`, and `applyNote` is exactly 0 or 1. Track, instrument, note and velocity must be in range, and note-on velocity must be positive. `applyNote=1` performs the same native note operation as the ordinary API. `applyNote=0` records the command's applied position without changing voices. It preserves the current convention of recording physical key release while sustain may defer the sounding note-off. This does not record CC64 automation.

Admission reserves both a command slot and one of the 4,095 usable acknowledgement slots. Return 0 queues nothing and does not produce an acknowledgement. The host can fall back to the ordinary note API to keep performance responsive, but must mark the recording edge unavailable rather than invent its position. Each accepted request eventually produces one `STInputAck` through the separate `st_engine_pop_input_ack` ring. If no audio callback runs, delivery cannot be promised; the host must bound request ownership/waiting, discard stale results, and must not retry a possibly already queued note because its acknowledgement is late.

The existing serialized control producer owns submission. One serialized consumer drains acknowledgements. A dedicated control-thread timer can safely drain concurrently with the audio producer because the pop operation touches only the SPSC ring and an atomic reservation count; engine lifetime must stay pinned, and there must never be a second consumer on the audio thread or elsewhere. A concurrent producer can refill commands during render, so each opt-in acknowledgement batch is capped at the fixed pending buffer capacity. Slot reservations include both pending commands and produced acknowledgements, and are returned only when an acknowledgement is popped. No callback allocation or lock is added.

## Clock provenance

An acknowledgement is stamped at the first audio sample to which its command batch applies, after row-boundary resolution. It carries the native pattern index, integer row and sequence occurrence, so the onset target comes from that frame rather than periodic status. `renderFrame` is the engine's processed-sample count. `graphFrame` is the original graph sample coordinate for cached bus rendering, or `INT64_MIN` for direct rendering. Overlapping cached prefixes do not consume commands or duplicate acknowledgements.

This is **applied-native-input-edge timing**, not historical hardware MIDI packet timing or a timestamp at JavaScript receipt. CoreMIDI timestamp preservation and host-time-to-render-frame scheduling remain a separate feature. A capture-only edge has this same provenance even though it does not end a sounding voice.

Usable live endpoints require `status == ST_INPUT_ACK_APPLIED` and `flags & ST_INPUT_CLOCK_PLAYING`. `ST_INPUT_ACK_DISCONTINUITY` explicitly marks a command whose run changed before its audio frame, including a Seek or Stop later in the same command batch. `ST_INPUT_ACK_CONTROL_FLUSH` identifies commands consumed by zero-frame/control checkpoint work; they have no applied audio endpoint. Never use pattern/row or distance from an invalid acknowledgement for insertion. The flags also identify mapped timing and recording intent; stopped edge capture remains acknowledged but cannot establish a live note duration.

`distanceBeats` measures nonnegative musical travel in quarter-note beats. It need not begin at zero. It increases across every normal mapped or fixed song loop and mapped pattern loop, including complete cycles between UI updates. Fixed-tempo Pattern mode already has an unwrapped native position. Normal tempo or meter boundaries do not interrupt a recording run.

`runID` is independent of the existing clock epoch. Play/restart, Seek, Stop, Panic, checkpoint restore, graph clock reset, and semantic timing/arrangement/loop-domain edits create a new run. Ordinary loop wraps, record-arm changes, instrument/mix edits and timing publication with identical revision preserve it. Song-end changes from audio clips and changes to an auditioned unsequenced pattern are also domain edits. Run-ID exhaustion explicitly makes endpoints unusable rather than reusing an old run.

## Host and frontend contract

Keep a bounded request-local ledger containing session/project identity, native-pattern-index-to-saved-ID mapping, stable track/instrument identities and input provenance. A late acknowledgement must never attach to a replacement project. Use the acknowledged native onset pattern and row to establish the insertion target, or reject a mismatch explicitly. Convert UInt64 request/run/revision values to canonical decimal strings at the JSON boundary.

Both note-on and note-off paths need matching endpoints, including the MIDI early-return release path and computer-keyboard requests. Do not begin computer recording from stale status and later apply only a correct duration to the wrong row. Forward `recordingClock: {distanceBeats, runID, timingRevision}` only for a usable endpoint. If either endpoint is missing, a run/revision changes, or the captured musical edit signature changes, retain the default gate and report that exact duration was unavailable.

For a mapped gate, divide the endpoint distance by the captured onset row's per-voice beat spacing: `(1 ± Float32(swing)) / LPB * (1 - Float32(microtiming)) / ratchet`. Match native clamping and the second FX column's precedence. Keep the onset project/row/step snapshot and reject later geometry changes. Shared chord notes use the first onset and last release under the existing tracker-step gate model. Native spacing metadata could replace this duplicated calculation later; this API does not claim to provide it.

## Pure verification

`cargo test -p tracker-engine --release --test engine_input_ack` (in `rust/`) runs the focused groups; a debug run (without `--release`) adds overflow and bounds checks. Tests cover exact onset rows at tempo/meter and swing boundaries; multiple loop wraps; arm and publication stability; Seek/Stop/restore ordering; zero-frame outcomes; strict IDs and saturation; cache overlap; capture-only sustain behavior; ordinary-versus-opt-in PCM equivalence; 20,000 concurrent producer/consumer edges; and measured zero render-thread C++ allocations. Existing engine/timing tests and pre-map golden PCM/events are checked separately. This is core evidence, not a claim of completed host/frontend recording integration.
