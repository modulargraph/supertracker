# Track Freeze — keyboard workflow

## How it works

Native freeze checks cover collection of song/head/loop prints, repeated Save As, moved-folder Open, exact-content relinking and preservation of source freshness across verified relocation.

A simple, robust Freeze/Unfreeze is implemented on top of the existing offline track bounce.

- **Host** (`st_audio::freeze`, registered in `st-host`): commands `freeze.track {track, tail?, maxTail?, method?, patterns?, monitor?}`, `freeze.unfreeze {track}`, `freeze.status`; progress events `freeze.progress {track, progress, phase, recording}`. The host projects every published project: a frozen track (`tracks[i].frozen`, a small record naming the print WAV) loses its plug-ins (the rack unloads them — CPU released), notes, source automation, original clips and live line input in the Host project, and gains a sample-aligned engine clip of the print on the same track. Canonical notes, instruments, clips, line-input routes and plug-in descriptors **with captured state** stay in the project; snapshots, `plugins.changed`, `plugin.move`, `routing.apply` and `timing.apply` replies re-add dormant descriptors so the UI never drops them. Plug-in load/remove/move/editor/preset on a frozen track is refused with “Unfreeze it to change its plug-ins.”
- **Print point (gain staging)**: post-insert, pre-fader — “instrument + inserts”. `audio.export` track mode renders the song with the track centred, unmuted, sends zero, master unity, mix automation and mix step commands removed, latency-trimmed (frame 0 = song frame 0), float 48 kHz. Fader, pan, mute, solo, sends, mix automation and volume/pan/delay/reverb step commands stay live and are applied once, after the print.
  - Standard routing already has the fader after the inserts: the print is at unity and exact.
  - The flat mixer applies track volume × master *before* the inserts. A nonlinear insert (compressor, saturator) heard that level live, so the inserts are printed at the live pre-insert gain (`frozen.printGain` = volume × master, 0.25…2, only when the track has inserts) and the print clip plays at `1 / printGain`. Unchanged faders are therefore exact even for nonlinear inserts; later fader moves act after the printed inserts. Remaining flat difference: the native delay/reverb sends of the frozen track hear the printed inserts (live they tapped the instrument before them); the freeze reply’s `notes` says so when such a send is up.
- **Tail length**: `tail` (seconds) gives a fixed tail. Omitted (the dialog’s default *Auto tail*), every print is rendered with `maxTail` (default 10 s, at most 30) and then cut where it stays below the silence threshold (−90 dBFS offline, −66 dBFS for recorded hardware with its noise floor) plus 20 ms. Because the print is rendered through the real chain, anything that ends the sound early — OFF, CUT, a choke, a short release, a gate on the last row — gives a short tail automatically; a long reverb keeps ringing up to the bound. `frozen.tailMode` records the choice. A pattern’s loop print wraps `1 + ⌈1.5 × head tail / pass⌉` passes (at least 2) in auto mode, `1 + ⌈tail / pass⌉` with a fixed tail.
- **Undo/Save**: Freeze and Unfreeze are each one ordinary project mutation (the fresh plug-in state is written into the baseline first), so Undo/Redo/Save/Open need nothing special.
- **Protection**: `ui/freeze.js` blocks edits (notes, step/source FX, source automation, referenced instruments, the track’s plug-ins, clips and line input, tempo, sequence, pattern lengths of sequenced patterns, track removal) with an explanation and an **Unfreeze…** action. The Host also reports a fingerprint mismatch as “Frozen · source changed”, and a missing print as “Frozen · unavailable”.
- **Refused shapes** (clear message): a send or output routed *into* the track, pre-insert sends/sidechain taps from the track, playback running, recording. Hardware tracks offline (see below).

## Loops and pattern switches (tails over the boundary)

- **Song mode, continuous song**: the song print is one continuous render, so tails of one pattern over the next are exact.
- **Song mode, Loop song** (whole song): the print clip stops at the musical end (loop length unchanged) and its tail — the frames past `musicalFrames` — is played by an engine *song tail* (`add_song_tail_clip`) from the next pass’s frame 0, exactly where the live chain rings over the loop point. The live loop releases held notes at the wrap; the print released them at its end, so the overlap matches (engine test: 2.5 looping passes, max diff 7e-9; without the song tail 0.054). Several overlapping tails (a song shorter than its tail) each sound. Stop/Seek/Play/Panic silence it. A non-looping song and every export (exports never loop) play the whole printed tail, so the natural song end moves out by the printed tail.
- **Pattern mode**: every pattern the track uses is printed twice, with the same tail: a **head** print (one pass + tail) and a **loop** print (the pattern rendered repeatedly, trimmed to its last pass + tail, so the previous passes’ tails are inside it). Stored as `frozen.patternPrints[] {pattern, path, sha256, frames, passFrames, passes, loop: {path, sha256, frames}}`; played by `add_pattern_clip`, aligned to the rows (Play from the cursor row, Seek, loop-range jumps and pattern changes re-align). After a natural wrap of the same pattern the loop print plays from 0 and the old print is *not* continued (its tail is already in the loop print: no doubled tail). When a pattern hands over to another at its natural end, the previous print keeps sounding as a tail under the next one (no cut tail), and the next one starts from its head (which holds no foreign tail). **Pattern export** plays the head print from beat 0 with its whole tail.

Documented semantic limits:

1. Pattern mode: (a) Play from a cursor row other than 0 also plays, during that first partial pass, the printed tails of notes that started before the cursor row; from the first wrap on it is exact. (b) A loop range that does not end on the pattern’s last row cuts the print at each jump back (live voices would ring on). A song *section* loop or a queued jump in Song mode likewise drops the tail at its jump (only whole-song loops get a song tail). (c) The loop print captures one steady-state pass: effects/instruments whose tail exceeds the printed tail by more than a pass, or that vary from pass to pass (DLSMusicDevice, free-running LFOs, random/probability), repeat that captured pass. (d) A pattern change mid-pass (not at the natural end) cuts the old print. (e) A print’s tail is the chain ringing out with nothing after it: notes held across the end of a head print are released there (live they would sustain into the next pattern until its next note or OFF), and a CUT/choke on the next pattern’s first row silences a live voice that the printed tail lets release. The loop print keeps held notes across its own wrap. Live audition and computer-keyboard/step notes on a frozen track show a message instead of sounding; hardware MIDI input routed to a frozen track is silently ignored.
2. Mixer: see *Print point* above (flat sends hear the printed inserts).
3. Explicit Stop silences the print immediately (live plug-ins would ring out).

## Latency compensation

A frozen track runs no plug-ins and has no line input, so its source latency is zero and it no longer counts in the delay-compensation plan: other tracks are not delayed for a plug-in that is no longer running (`compensationAfter` in the reply; the plan drops to 0 when the frozen track held the only latency). The print itself was trimmed by the full compensation of its render, so its frame 0 is song frame 0, and the zero-latency clip is then delayed by the track compensator like any other aligned source — it lands where the compensated live track played. MIDI clock lead and automation offsets follow the new plan. Unfreeze restores the plug-ins and the plan.

## Hardware tracks: freeze by recording

> **Not implemented in the host yet.** `freeze.track` with `method: "record"` is refused, as are live line inputs into track strips. The design below is what the interface expects.

A track whose sound is made outside the computer — a live line input (the hardware return of a synth), or an external MIDI instrument — cannot be rendered offline; offline freeze refuses it with “Choose Freeze by recording”. **Freeze by recording** (`method: "record"`, the dialog’s *Record and freeze* for live-input tracks) plays the print project once in real time from the song start (Song mode, no loop) and captures the track strip of the flat mixer (a routed project plays flat for the take; its print equals the routed strip after the inserts) — after the line input, the track’s inserts and its plug-in/hardware-return delay compensation — through a tap on the strip. At that point every track is aligned, so content at graph frame T is song frame `songFrame(T − compensation)`; the native clock (`clock_span` with that upstream latency) gives the mapping, and each tap buffer is written at its song frame. The recorded print therefore lands exactly where the compensated live return did, with the same `hardwareReturnSeconds` estimate. A take ends at the musical end plus the tail (auto: when the return stays below −66 dBFS for 0.5 s, bounded by the maximum tail), and fails clearly if playback stops, jumps or restarts, or the strip delivers no audio. With `patterns` (default on) each pattern’s head and loop prints are recorded too, as separate takes; off, the track is song-only in Pattern mode (badge). `monitor: false` mutes the main output during the takes (the strip is captured upstream).

While frozen, the track’s editor plug-in is unloaded and its notes are not sequenced, so **the hardware receives no MIDI from this track** and is free to play another part; the line input is closed (no doubled return, no hardware-return latency in the plan). The canonical project keeps the editor with its state and the line-input route, so Unfreeze restores both. Freeze by recording needs the flat mixer (routing off) and the return as this track’s line input. What cannot be verified without the hardware: the analogue path itself (the take is as accurate as the device’s reported latency, like live monitoring).

## Suspending silent plug-ins (not shipped)

Suspending plug-ins while they are temporarily silent was considered and left out. A plug-in that receives no input and outputs silence is not necessarily idle: reverbs/delays ring past the last input, synths hold envelopes and LFOs, look-ahead or FFT processors keep internal buffers, and many plug-ins report no or wrong `tailTime`. Bypassing or not rendering it changes its state (the next note starts from a different filter/LFO phase), skipping and resuming render calls can click or desynchronise VST3/AU sample positions and parameter queues, and hardware editors must keep sending MIDI. Hosts that do it (“sleep”/“auto suspend”) rely on per-plug-in opt-in and a measured silent output over a guard period longer than the declared tail, and still re-render on any input or parameter change. Recommendation: if wanted, implement it per insert as an explicit opt-in (“Suspend when silent”), resume on the first non-silent input or automation event with a pre-roll, require the output to be below −120 dBFS for max(tailTime, 2 s), never for instruments or hardware editors, and measure the saving first — Freeze is the safe way to release a heavy chain.
